# Дополнение к запросу на валидацию: чем мы ищем технологии

Дополнение к `hackathon/prompt-gpt6-astra-radar-validation.md`, написано 26.09.2026
через несколько часов после основного запроса. Читать вместе с ним. Рабочий файл
команды, не для публикации.

Тема дополнения: источники поиска. Появились замеры, которых в основном запросе не
было, и начата смена архитектуры сбора. Нужен твой вердикт по ней тоже.

## 1. Главное: Yandex Search API работает, но отдаёт не тот слой интернета

Формулировка «поиск не работает» была бы неверной, не опирайся на неё. API
отвечает, загрузка страниц идёт на 91 %, за четыре прогона получено 475
кандидатов. Проблема в составе выдачи.

Классификация 900 позиций выдачи из четырёх живых прогонов по области «Защита ИИ».
Классификатор грубый, по регулярным выражениям на хост; он сохранён в репозитории
как `radar/hoststats.py`, запускается `python -m radar.hoststats` и воспроизводит
все числа этого раздела из файлов прогонов:

| слой | доля позиций |
|---|---|
| прочее: мелкие сайты, по одному-два на хост | 74,9 % |
| SEO-подборки вида «50 AI security startups to watch» | 13,4 % |
| СМИ и блоги | 5,1 % |
| первоисточники: arXiv, GitHub, стандарты, крупные вендоры | 3,3 % |
| видео и соцсети | 3,2 % |

Частности, которые стоит проверить самостоятельно по `radar-runs/*/hits.jsonl`:

- 481 разный хост на 900 позиций, то есть выдача рассыпана по длинному хвосту.
- Самый частый хост — `youtube.com`, 25 позиций.
- На линзе funding SEO-подборки дают 36,0 % позиций, первоисточники — 0,5 %.
- Из 475 кандидатов первоисточники дали 17, то есть 3,6 %.

Поправка к первой версии этого файла: я писал «904 позиции» и «484 хоста». Это
было по всем папкам прогонов, включая один прерванный без манифеста. При отборе
только живых прогонов, как это делает сохранённый скрипт, получается 900 позиций и
481 хост. Доли не изменились.

Классификатор считай оценкой, а не фактом: 74,9 % «прочего» — это в основном мелкие
вендорские блоги и незнакомые домены, среди них есть и содержательные. Но вывод от
этого не меняется: экспертную таблицу заказчика собирали не по таким страницам.

## 2. Отсюда вывод, который нужно оспорить или подтвердить

Общий веб-поиск ранжирует по популярности, а слабый сигнал по определению
непопулярен. Пять эталонных категорий, которых мы не нашли (№22 governance под EU
AI Act, №23 дифференциально-приватные синтетические данные, №24 конфиденциальный
инференс в TEE, №48 machine unlearning, №52 мониторинг chain-of-thought), не
существуют как продукты и в продуктовой выдаче появиться не могут. №50 из
засчитанных сомнительно — это черновик IETF, он лежит в datatracker.

Поэтому я начал делать не «другой поиск», а **источник под линзу**:

- preprint и research → академические базы;
- standard → IETF datatracker, NIST, официальные документы ЕС;
- product и prototype → GitHub и Hugging Face, плюс веб-поиск;
- funding → Yandex Search API, потому что открытых баз сделок без зарубежной карты
  у нас нет.

## 3. Что сделано и что выяснилось про arXiv

Написан провайдер `radar/arxiv.py`: построение запроса из значимых слов
подсегмента, окно 18 месяцев по дате подачи, разбор Atom, готовый
`DocumentSnapshot` прямо из аннотации — то есть шаг загрузки и разбора HTML для
таких попаданий не нужен вовсе.

Живые вызовы упёрлись в отказ, и причина не та, которая кажется:

- запрос `all:electron` (заведомо популярный, почти наверняка закеширован на
  стороне arXiv) отдаёт **200** и две записи;
- любой запрос, требующий живого поиска, отдаёт **406 с пустым телом**: и
  `all:zxqvwmt`, и `all:unlearning`, и фразовые, и с датой;
- не помогают ни `Accept: application/atom+xml`, ни `http://` вместо `https://`,
  ни выдержки 10, 30 и 60 секунд, ни интервал 3 секунды между вызовами.

Похоже на временную блокировку нашего адреса после пачки запросов при отладке:
кеш отдаётся, живой поиск отказан. Синтаксис запроса тут ни при чём, и 406 нельзя
трактовать как «статей нет». В провайдер добавлены выдержки и счётчик отказов,
чтобы такая ошибка попадала в отчёт прогона, а не выглядела пустым результатом.

**Статус на момент письма: провайдер arXiv не подтверждён живым вызовом.**

## 4. OpenAlex проверен живьём и закрывает те же пробелы

Ключ не нужен, ограничения щедрые, ответ JSON. Четыре пробных запроса по
ненайденным категориям, фильтр `title_and_abstract.search` плюс
`from_publication_date:2025-04-01`, сортировка по дате:

| запрос | работ в выборке | верхняя запись |
|---|---|---|
| machine unlearning | 1371 | 24.09.2026, arXiv, про обход unlearning через токенизацию |
| chain-of-thought monitoring deception | 31 | 14.09.2026, arXiv, обход мониторинга цепочки рассуждений |
| differentially private synthetic data | 409 | 24.09.2026, синтетические табличные данные с DP |
| confidential inference trusted execution | 112 | 24.09.2026, arXiv, доверенная среда для приватных вычислений |

Важное следствие: OpenAlex индексирует и arXiv, и Zenodo, то есть заменяет
провайдер arXiv целиком, пока тот заблокирован. И `meta.count` с группировкой по
году даёт **рост публикаций по годам** — ту самую количественную меру усиления
сигнала, которой у нас нет ни одной и без которой нечем ранжировать ТОП-15.

Замеченная проблема качества: Zenodo отдаёт дубликаты одной работы и заметную
долю слабых текстов. В выборках выше дубли видны прямо в трёх запросах из четырёх.

## 5. Поправка к основному запросу

В разделе 4 основного запроса сказано «3 из 16 — пары, которые я готов защищать:
№2, №3, №4». После разбора утечки эталона в промпт извлечения (раздел 6, пункт 2
того же файла) **надёжны только №2 и №3, то есть 2 из 16**. Кандидат, по которому
засчитана №4, назван дословно как пример из промпта. Считай верной цифру 2.

## 6. Дополнительные вопросы, нумерация продолжает основной запрос

11. **Источник под линзу.** Верна ли сама идея, или правильнее оставить один
    источник и лечить запросы? Что мы теряем, разводя линзы по источникам: пул
    перестаёт быть сравнимым между областями, возникает разная полнота по линзам.
12. **Какие источники под какие линзы.** Оцени по отдаче и по стоимости внедрения:
    OpenAlex, Crossref, Semantic Scholar, arXiv, GitHub, Hugging Face, IETF
    datatracker, NVD/CVE, NIST, официальные документы ЕС. Ограничение: зарубежной
    карты у нас, скорее всего, нет, поэтому Exa, Tavily, Brave, Serper и Crunchbase
    считай недоступными, если не обоснуешь обратное. Нужны конкретные конечные
    точки и формы запроса, а не названия сервисов.
13. **Нужен ли Яндекс.** Остаётся ли для него задача, кроме сделок и пилотов? Если
    да, какая, и стоит ли ограничивать его через `site:` до списка первоисточников.
14. **Риск перекоса в науку.** По любому запросу OpenAlex отдаёт сотни и тысячи
    работ, а рыночные категории эталона (№2, №3, №4) пришли из веба. Как
    балансировать пул, чтобы препринты не вытеснили рыночные категории, и как
    удерживать баланс автоматически, а не подбором вручную.
15. **Качество академических источников.** Дубликаты Zenodo, препринты без
    рецензирования, самоцитирование. Фильтровать по источнику, по цитируемости, по
    типу работы? Не убьёт ли фильтр по цитируемости именно слабый сигнал, у
    которого цитирований ещё нет?
16. **Метрика роста.** Как корректно считать усиление сигнала по числу публикаций
    по годам: какое окно, нормировать ли на общий рост области, какой порог считать
    сигналом. Это нужно для второй половины воронки — фильтра зрелости и
    ранжирования ТОП-15. Учти, что за 2026 год данные неполные.
17. **Инфраструктура.** Сейчас всё хранится файлами: 81 МБ на четыре прогона одной
    области, из них 14–20 МБ на прогон — сырой HTML. Оправданы ли в оставшиеся два
    дня SQLite поверх прогонов, аренда сервера и настоящая БД, или это отвлечение
    от покрытия? Учти, что стенд экспертной разметки для Олега всё равно требует
    хоста и одновременной записи несколькими людьми.
18. **Вежливость к бесплатным API.** Прогон делает 36 поисковых запросов. Как не
    попадать в блокировку arXiv и не нарушать правила OpenAlex при десяти прогонах
    в день, и какие лимиты считать безопасными.

## 7. Как проверить мои числа самостоятельно

Классификация хостов сохранена в репозитории: `radar/hoststats.py`. Запуск
`python -m radar.hoststats` (по умолчанию область «Защита ИИ», `--area` и `--top`
меняются флагами). Скрипт читает `hits.jsonl` и `candidates.jsonl` всех прогонов с
`mode == "live"`, берёт хост из URL и относит его к слою первым совпадением.

Регулярные выражения целиком, как они применялись:

    PRIMARY = (arxiv\.org|openreview|acm\.org|ieee|nist\.gov|europa\.eu|iso\.org|ietf\.org|
               nvd\.nist|cve\.org|github\.com|huggingface\.co|openai\.com|anthropic\.com|
               google|microsoft|cloudflare|nvidia|aws\.amazon|cisa\.gov|owasp\.org|mitre\.org)

    NEWSY   = (techcrunch|venturebeat|reuters|bloomberg|calcalistech|darkreading|theregister|
               zdnet|forbes|axios|ft\.com|wsj|habr\.com|dev\.to|medium\.com)

    FARM    = (growthlist|pitchwise|roundfunded|seedtable|spectup|eu-startups|datapile|basg\.co|
               futureagi|securityelites|grieccotech|unite\.ai|aiagentsquare|intelscroll|
               nerdleveltech|thestackunderflow|securitywall|hub\.causo|ai-manual)

    SOCIAL  = (youtube|linkedin|twitter|x\.com|reddit|facebook|tiktok)

Порядок проверки: PRIMARY, SOCIAL, FARM, NEWSY, остальное — «прочее». Списки я
набирал вручную по верхним 25 хостам выдачи, то есть они неизбежно смещены в
сторону того, что попалось в этой области. Три возражения, которые я считаю
законными и которые прошу проверить:

- `github.com` отнесён к первоисточникам целиком, хотя блог-посты на `github.blog`
  и README рекламного характера — не одно и то же;
- `habr.com` и `dev.to` отнесены к СМИ и блогам, хотя иногда несут первичное
  техническое описание;
- в FARM попали хосты, которые я счёл подборками по одной-двум страницам, —
  `futureagi`, `intelscroll`, `securitywall`, `hub.causo`, `ai-manual`. Именно из
  `futureagi` пришли кандидаты, по которым засчитаны №3 и №4, так что ярлык
  «подборка» для этого хоста может быть несправедлив.

Если поправишь списки и доли изменятся существенно, вывод раздела 2 нужно
пересматривать вместе с ними.

Пробы OpenAlex: `https://api.openalex.org/works` с параметрами
`filter=title_and_abstract.search:<запрос>,from_publication_date:2025-04-01`,
`sort=publication_date:desc`, `per-page=3`. Без ключа, с вежливым User-Agent.

Пробы arXiv: `https://export.arxiv.org/api/query?search_query=all:electron` даёт
200, `...?search_query=all:unlearning` даёт 406 с пустым телом.

Ограничения прежние: платные прогоны не запускай, код не меняй, разделы 0–13
основного отчёта не трогай, ответ пиши в `hackathon/review-radar-validation-gpt.md`
одним файлом вместе с ответами на вопросы 1–10 из основного запроса.

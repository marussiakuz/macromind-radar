# Архитектура TechTrendSearcher

Приложение состоит из интерфейса React/TypeScript и сервиса FastAPI. Docker собирает оба компонента; FastAPI раздаёт интерфейс и API с одного адреса. Основная языковая модель работает через отдельный HTTP API. Для сравнения текстов используется локальная модель эмбеддингов на CPU.

## Путь запроса

1. Интерфейс отправляет тему в `/api/search`. Сервис проверяет токен, квоту и расчётный бюджет.
2. Если готовый совместимый разбор уже есть, сервис возвращает его. Деморежим читает только сохранённые карточки.
3. Новый запрос проходит предварительную проверку смысла. Модель строит дерево поднаправлений, по которому выполняется поиск.
4. Загрузчик получает HTML и текстовые PDF. Отбор распределяет документы между темами и источниками.
5. Модель извлекает категории и цитаты. Код проверяет соответствие цитаты её документу.
6. Сервис проверяет связь с темой, признаки ранней стадии, зрелость и опровержения. Близкие категории объединяются только при совпадении механизма и объекта.
7. Для итоговых кандидатов собираются дополнительные сведения. Интерфейс показывает до 15 карточек и причины исключений.

## Основные модули

| Модуль | Ответственность |
| --- | --- |
| `public.py`, `server.py` | HTTP API, очередь, квоты, демонстрация и карточки |
| `config.py`, `ledger.py` | Настройки, модели данных и учёт расходов |
| `discovery.py`, `search.py`, `openalex.py` | План поиска и провайдеры источников |
| `fetch.py`, `selection.py`, `passages.py` | Загрузка, отбор документов и фрагментов |
| `extract.py`, `dedup.py`, `merging.py` | Извлечение, проверка цитат и объединение |
| `assessment.py`, `maturity.py`, `feasibility.py`, `sequential.py` | Проверка кандидатов |
| `rank.py`, `players.py`, `dossier.py`, `export_ui.py` | Упорядочивание и подготовка карточек |
| `reference.py`, `evaluate.py`, `judge.py`, `metrics.py` | Отдельные инструменты проверки качества |

`reference.py` нужен только для сравнения с закрытым эталоном. Его файл не требуется для открытого запроса, деморежима и обычного запуска приложения.

## Состояние и повторный запуск

Каждый анализ пишет отдельный каталог в `radar-runs`. Совместимость пула определяется версией конвейера, планом, лимитами и настройками модели. Готовые карточки имеют отдельную версию. Кэш ответов модели учитывает адрес сервера и параметры запроса.

Расходы сохраняются в `ledger.json` под файловой блокировкой. Квоты — в `public-quota.json`. В Docker весь каталог подключён как постоянный том. Новый журнал имеет нулевые лимиты.

Очередь и прогресс текущих задач хранятся в памяти. Поддерживается один процесс сервиса и один активный анализ; при перезапуске незавершённая задача автоматически не возобновляется. Для нескольких рабочих процессов потребуется внешняя очередь и общее хранилище задач.

## Подключение в контуре заказчика

Языковую модель можно заменить настройками `.env`; изменения кода не нужны при совместимом Chat Completions API. Веб-поиск по-прежнему использует Yandex Search API. Полностью изолированный от интернета режим сейчас ограничен просмотром сохранённых разборов.

Публичное размещение использует дополнительный Caddy-прокси для HTTPS. Параметры запуска и ограничения доступа описаны в [инструкции развёртывания](deploy-mvp-2026-09-29.md).

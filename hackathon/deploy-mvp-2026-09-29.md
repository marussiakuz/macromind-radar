# Развёртывание работающего MVP на своём сервере

29.09.2026. Цель — публичный HTTPS-адрес, по которому жюри вводит **свой** запрос и
получает настоящий прогон, а не сохранённую выгрузку. Все команды проверены по составу
файлов репозитория; сам сервер ещё не арендован, поэтому шаги 2–6 на живой машине не
прогонялись — это инструкция, а не журнал выполненного.

## 0. Что понадобится

| | |
|---|---|
| Сервер | 2 vCPU, 4 ГБ RAM, 30 ГБ SSD, Ubuntu 24.04. GPU не нужен: эмбеддинги считаются на процессоре, модель вызывается по API |
| Имя | свой домен (`radar.example.ru`) либо, если домена нет, имя вида `203-0-113-7.sslip.io` — оно разворачивается в этот же IP, и Let's Encrypt выдаёт на него сертификат |
| Ключи | `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, по желанию `OPENALEX_API_KEY` |
| Деньги | живой прогон ≈ 90 ₽ (около 60 ₽ поиска и 30 ₽ модели). Лимиты по умолчанию: 6 прогонов в сутки всего и 2 с одного адреса |

Образ занимает около 2 ГБ: в него кладётся процессорная сборка torch и модель
`intfloat/multilingual-e5-small`. Модель обязана быть внутри образа — в рантайме
`radar/vectors.py` открывает её с `local_files_only=True` и в сеть за ней не идёт.

### Если сервер берётся в Yandex Cloud

Compute Cloud → Создать ВМ. Значения, которые важны:

| Поле | Значение | Почему |
|---|---|---|
| Образ | Ubuntu 24.04 LTS | семейство `ubuntu-2404-lts` в каталоге `standard-images` |
| Платформа | Intel Ice Lake (`standard-v3`) | самая дешёвая современная |
| vCPU / RAM | 2 / 4 ГБ | эмбеддинги и разбор PDF считает процессор; на 2 ГБ возможен OOM при сборке образа |
| Гарантированная доля vCPU | **100 %** | на 20 % загрузка модели и кодирование растягивают прогон на десятки минут |
| Диск | SSD, 30 ГБ | образ ≈ 2 ГБ, система ≈ 3 ГБ, прогон ≈ 20 МБ |
| Прерываемая | нет | прерываемую могут погасить в любой момент, а адрес стоит в заявке |
| Публичный адрес | статический | иначе имя для сертификата меняется при перезапуске |
| Security group | вход TCP 22, 80, 443 с 0.0.0.0/0; выход — всё | порт 80 обязателен для проверки Let's Encrypt |

Ориентир по цене: около 80–90 ₽ в сутки (вычисление ≈ 3 ₽/час, диск ≈ 8 ₽/сутки, статический
адрес ≈ 5 ₽/сутки). Точную сумму считает калькулятор Yandex Cloud.

Отдельная удача этого хостинга: поиск и модель — сервисы того же провайдера, то есть вызовы
идут внутри его сети.

### Домен и записи DNS

Куплен `techtrendsearcher.ru`. В панели регистратора нужны две записи типа **A**:

| Имя | Тип | Значение | TTL |
|---|---|---|---|
| `@` (или пусто) | A | публичный IP сервера | 600 |
| `www` | A | тот же IP | 600 |

`.ru` делегируется не мгновенно — от четверти часа до суток. Проверять так:

```sh
dig +short techtrendsearcher.ru
```

Пока записи не разошлись, разворачиваем на имени `IP-с-дефисами.sslip.io`: оно
разрешается в тот же адрес сразу, и Let's Encrypt выдаёт на него сертификат. Когда `dig`
покажет нужный IP, меняем одну строку `RADAR_HOST` в `.env` и перезапускаем
(`docker compose up -d`) — Caddy получит сертификат на домен сам.

**Один адрес на всё.** Интерфейс и сервис отдаются с одного имени: `/` — страница
аналитика, `/api/*` — сервис, `/docs` — Swagger. Так не нужен CORS, и со страницы по https
не приходится обращаться к сервису по http (браузер это запрещает).

## 1. На ноутбуке: собрать посылку состояния

```sh
cd hackathon
.venv/bin/python deploy/pack-runs.py
```

Получается `deploy/runs-seed.tar.gz` — около 300 КБ: по три файла на каждый сохранённый
прогон (`manifest.json`, `candidates.jsonl`, `cards.json`) плюс `ledger.json` с учётом
расходов. Полные прогоны весят 415 МБ, потому что хранят снимки страниц; серверу они не
нужны — карточки уже посчитаны.

Зачем это нужно: с этой посылкой сервер сразу умеет мгновенно и бесплатно отдавать
разборы по пяти областям (Edge, Роботы, Защита ИИ, Финтех, Индустриальный ИИ, по 15
позиций), а `ledger.json` не даёт ему решить, что денег больше, чем есть.

Скрипт отбрасывает прогоны с устаревшей версией карточек: иначе повторный запрос на
сервере пересчитал бы их за деньги.

## 2. Сервер: код и докер

Два способа. **Проще — скопировать файлы с ноутбука**, тогда не нужен публичный репозиторий:

```sh
# с ноутбука, из каталога проекта
ssh ubuntu@СЕРВЕР 'sudo mkdir -p /opt/radar && sudo chown $USER /opt/radar'
rsync -av --exclude '__pycache__' --exclude '.venv' \
      hackathon/radar hackathon/samples hackathon/deploy \
      hackathon/requirements.txt hackathon/Dockerfile \
      hackathon/docker-compose.yml hackathon/Caddyfile \
      hackathon/deploy/runs-seed.tar.gz \
      ubuntu@СЕРВЕР:/opt/radar/
# Собранный интерфейс: раздаётся с того же адреса, что и сервис
rsync -av --delete tech-trend-searcher/dist/ ubuntu@СЕРВЕР:/opt/radar/ui/
scp hackathon/.env ubuntu@СЕРВЕР:/opt/radar/.env      # ключи не печатаются в консоль
ssh ubuntu@СЕРВЕР 'sudo bash /opt/radar/deploy/remote-setup.sh'
```

`remote-setup.sh` ставит Docker, распаковывает посылку состояния, выставляет владельца
каталога прогонов, собирает образ, поднимает сервис и печатает проверку. Повторный запуск
обновляет образ и не теряет состояние.

**Через репозиторий** — если он уже публичный:

```sh
ssh ubuntu@СЕРВЕР
curl -fsSL https://get.docker.com | sh
sudo git clone https://github.com/marussiakuz/macromind-radar.git /opt/radar-src
sudo cp -r /opt/radar-src/hackathon /opt/radar
cd /opt/radar
```

## 3. Ключи и адрес

```sh
cat > /opt/radar/hackathon/.env <<'EOF'
YANDEX_API_KEY=...
YANDEX_FOLDER_ID=...
OPENALEX_API_KEY=...
RADAR_HOST=radar.example.ru
RADAR_DAILY_RUNS=6
RADAR_IP_DAILY_RUNS=2
RADAR_RUN_TIMEOUT=1200
EOF
chmod 600 /opt/radar/hackathon/.env
```

Файл `.env` закрыт белым списком в корневом `.gitignore` и в репозиторий не попадает.
После хакатона ключи стоит перевыпустить: они лежали на машине, к которой был открыт
доступ извне.

Если живой прогон нужно отдать только жюри, добавить `RADAR_PUBLIC_TOKEN=какая-то-строка`:
тогда запуск требует заголовок `X-Radar-Token` или параметр `?token=`, а сохранённые
разборы остаются открытыми.

## 4. Состояние и запуск

```sh
# посылка с ноутбука
scp hackathon/deploy/runs-seed.tar.gz root@СЕРВЕР:/opt/radar/hackathon/
# на сервере
cd /opt/radar/hackathon
tar -xzf runs-seed.tar.gz          # появится radar-runs/ с прогонами и учётом расходов
chown -R 1000:1000 radar-runs      # контейнер работает не от root и иначе не запишет учёт
docker compose up -d --build       # первая сборка 5–10 минут: torch и модель
```

Про `chown`: приложение внутри контейнера работает от пользователя с идентификатором 1000,
а распакованные файлы принадлежат root. Без этой строки сервис прочитает сохранённые
разборы, но не сможет записать расход и квоту — и упадёт на первом живом прогоне.

Порты 80 и 443 должны быть открыты — Caddy получает сертификат сам, при первом обращении.

## 5. Проверить, что MVP действительно работает

```sh
curl -s https://ВАШ_АДРЕС/api/health     # {"ok":true,"demo":false,"runs":6}
curl -s https://ВАШ_АДРЕС/api/limits     # остаток корзин, квота, тайм-аут
open https://ВАШ_АДРЕС/docs              # Swagger с четырьмя эндпоинтами

# мгновенный сохранённый разбор: денег не тратит, квоту не тратит
curl -s -X POST https://ВАШ_АДРЕС/api/search \
  -H 'Content-Type: application/json' -d '{"query":"Финтех"}'
```

Живой прогон стоит проверить **один раз** и до защиты: ввести запрос, которого нет среди
сохранённых, и дождаться конца. Он длится 7–11 минут и тратит около 90 ₽. Если корзины не
хватает на полный прогон, сервис откажет сразу с числами — это лучше, чем оборванный на
середине прогон, потративший поисковую корзину впустую.

## 5а. Пополнение бюджета

Учёт считает остаток от разрешённых сумм минус расход, поэтому **пополнение счёта у
провайдера сервис сам не заметит**. После оплаты нужно записать пополнение:

```sh
docker compose exec radar python -m radar.ledger status
docker compose exec radar python -m radar.ledger topup \
    --id 2026-09-29-llm300 --llm 300 --reason "пополнение под публичный MVP"
```

`--id` — идентификатор разрешения: повторный запуск той же команды сумму не удвоит.
Пополнять можно одну корзину: на 29.09.2026 кончилась корзина модели (38 ₽) при остатке
поиска 537 ₽. Пока пополнение не записано, живые прогоны отклоняются с кодом 402 — по
делу, потому что денег на полный прогон действительно нет.

## 6. Интерфейс на GitHub Pages

Страница должна знать адрес сервиса. Один раз:

```sh
gh variable set RADAR_API --body "https://ВАШ_АДРЕС" --repo marussiakuz/macromind-radar
gh workflow run pages.yml --repo marussiakuz/macromind-radar
```

Сборка подставит адрес в `VITE_RADAR_API`. После этого на странице:

* ввод запроса запускает настоящий прогон на сервере;
* под полем видно, сколько живых прогонов осталось сегодня и хватает ли бюджета;
* если сервис недоступен, страница честно говорит об этом и открывает вшитый разбор.

## 7. Эксплуатация

| Задача | Команда |
|---|---|
| Логи сервиса | `docker compose logs -f radar` |
| Логи HTTPS | `docker compose logs -f caddy` |
| Обновить код | `git pull && docker compose up -d --build` |
| Остановить живые прогоны, оставив сохранённые | в `.env` поставить `RADAR_DAILY_RUNS=0`, затем `docker compose up -d` |
| Посмотреть расход | `docker compose exec radar python -c "from radar.ledger import Ledger; print(Ledger().remaining())"` |
| Сбросить суточную квоту | удалить `radar-runs/public-quota.json` |

Состояние живёт в `radar-runs/`: учёт расходов, квота, сохранённые разборы и новые
прогоны. Том подключён из каталога на хосте, поэтому перезапуск контейнера ничего не
теряет.

## 7а. Что помешало при первом развёртывании

Записано, потому что обе ловушки выглядят одинаково — `Permission denied (publickey)` — и
на них ушло больше часа.

1. **OS Login отменяет ssh-ключи из метаданных.** Если на машине включён «Доступ по
   OS Login», ключ из формы создания ВМ и файл `~/.ssh/authorized_keys` не используются
   вовсе: sshd спрашивает ключи у профиля пользователя в Cloud Organization. Класть ключ
   нужно туда: консоль → Organization → Пользователи → нужный пользователь → «SSH-ключи».
   Логин при этом не `ubuntu`, а сгенерированный, его показывает блок «Подключиться с
   помощью SSH-клиента» на странице ВМ. Для `sudo` пользователю нужна роль
   `compute.osAdminLogin`, а не `compute.osLogin`.

2. **Ключ с паролем не работает в неинтерактивном режиме.** `ssh -i ключ` с
   `BatchMode=yes` молча пропускает защищённый паролем ключ и возвращает ровно то же
   `Permission denied (publickey)`, что и отказ сервера. Отличить можно по отладке:

   ```sh
   ssh -vv -i ~/.ssh/ключ -l ЛОГИН СЕРВЕР true 2>&1 | grep -E "Offering|Server accepts"
   ```

   Если видно `Server accepts key` — сервер настроен верно, а мешает пароль ключа.
   Лечится один раз: `ssh-add --apple-use-keychain ~/.ssh/ключ`.

**Проверять в таком порядке:** сначала `Server accepts key` на своей стороне, потом
`/usr/bin/google_authorized_keys ЛОГИН | ssh-keygen -lf -` на сервере, и только затем
права, владельцев и конфигурацию sshd.

## 8. Что здесь честно не сделано

1. **Прогон нельзя прервать.** Сторож помечает задачу отказом по тайм-ауту (20 минут по
   умолчанию), и интерфейс перестаёт ждать, но поток конвейера при этом доживает своё:
   остановить его на середине нечем. Деньги, потраченные до тайм-аута, не возвращаются.
2. **Очередь на один анализ.** Второй запрос ждёт первый. Интерфейс сообщает об этом, но
   позиции в очереди не показывает.
3. **Квота по адресу обходится** сменой адреса. Это защита бюджета от случайного
   исчерпания, а не от целенаправленного.
4. **Ключи на сервере.** Они в `.env` с правами 600 и в переменных окружения контейнера;
   это обычная практика, но после хакатона их нужно перевыпустить.
5. **Живой прогон на публичном адресе проверен не был** — сервера на момент написания нет.
   Локально тот же код работает: ограничители покрыты девятью тестами
   (`radar/tests/test_public.py`), маршрут `/api/limits` отвечает.

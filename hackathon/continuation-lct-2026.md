| Сценарий | Постоянная машина | GPU |
|---|---|---|
| Минимальный API-стенд из первого отчёта | 4 vCPU / 16 ГБ RAM / 200 ГБ SSD | Отдельные сеансы по задаче |
| Комфортный API-стенд из обсуждения | 8 vCPU / 32 ГБ RAM / 300 ГБ SSD | Отдельные сеансы по задаче |

| Около 1 млн чанков, API-модель, активная фоновая обработка | Плановый ориентир **16 vCPU / 64 ГБ RAM / 500 ГБ–1 ТБ SSD** | По нагрузке; не обязательна только ради хранения векторов |
| Все выбранные модели локально | **16 vCPU / 120–128 ГБ RAM / 1 ТБ SSD** | **1 × RTX 6000 Pro 96 ГБ** |

Последние конфигурации — инженерные рекомендации, не новый аудит тарифов. Миллион векторов сам по себе не требует терабайта диска: запас относится к документам, версиям, индексам и обслуживанию всего приложения.

В предыдущем объяснении была исправлена неоднозначная фраза «GPU не нужна». **Постоянная собственная GPU необязательна лишь при вынесении большой LLM в API и достаточной измеренной скорости остальных этапов. Полностью локальный вариант с Qwen 27B/35B без GPU для нашей задачи не рекомендован.**

- PostgreSQL/обычный pgvector хранит данные и ищет векторы с использованием CPU, системной RAM и диска. VRAM не заменяет память БД.
- Создание embeddings — отдельная нейросетевая операция. GPU полезна для первоначального корпуса и больших обновлений.
- Готовые embeddings не пересчитываются на каждом запросе; пересчитываются новые/изменённые чанки и вектор запроса. Смена embedding-модели требует совместимой версии индекса или переиндексации.
- В живом поиске появляются новые источники. CPU-only embedding/reranking **не прошли проверку времени**, поэтому нельзя автоматически обещать отсутствие потребности в GPU.
- QLoRA и обслуживание живых запросов разводим по времени. Полное обучение 30–35B в этот план не входит.
- Постоянные данные БД и резервные копии должны сохраняться независимо от временных GPU-сеансов.

Для сервера нужны Linux, Docker, SSH, публичный HTTPS и стабильный исходящий доступ к API/источникам. Порт 1 Гбит/с — желательный инженерный ориентир, особенно при загрузке весов; это не гарантия скорости внешнего хранилища.

## 3. Полный RAG и расчёт pgvector

Рабочий контур: **загрузка документов → версии и разбор текста → чанки → embeddings → PostgreSQL/pgvector → поиск с метаданными/фильтрами → reranking → проверяемый ответ LLM с источниками**. Векторная БД сама не генерирует embeddings и не формирует ответ LLM.

Объём считаем по **чанкам**, не по количеству исходных документов. При одном embedding `vector(1024)` на чанк официальный размер значения — `4 × 1024 + 8 = 4104` байта:

| Чанков | Только значения vector(1024), GB = 10⁹ байт |
|---:|---:|
| 50 000 | 0,2052 ГБ |
| 100 000 | 0,4104 ГБ |
| 1 000 000 | 4,104 ГБ |

Это **не полный размер БД**. Добавляются тексты, метаданные, служебные структуры PostgreSQL, HNSW/другие индексы, WAL, версии и место для перестроения. Универсальный точный коэффициент размера HNSW не установлен. На реальном срезе измерять таблицу, индексы и полный каталог данных отдельно.

Индекс не обязан целиком помещаться в RAM, но кэширование рабочего набора ускоряет поиск. Нельзя выводить скорость из одного лишь количества GB векторов. Построение HNSW тоже конкурирует за RAM/CPU/диск; массовую загрузку и демонстрацию нужно развести либо ограничить ресурсы. Проверять полноту поиска с фильтрами, а не только задержку. Выделять БД на отдельную машину при измеренной конкуренции с ingestion или необходимости независимого обслуживания, не автоматически по достижении условного числа векторов.

## 4. Память моделей и 20 минут

Основные варианты первого отчёта сохранены: локальная **Qwen/Qwen3.6-27B-FP8**, альтернативная **35B-A3B FP8**; API — Qwen3.6-35B-A3B в Yandex, резерв по разделу 5 отчёта. Embedding и reranker — готовые Qwen3 0.6B.

Расчётные, **не измеренные** ориентиры из раздела 7:

- Qwen3.6-27B-FP8 при пяти последовательностях по 8k: примерно **34–39 GiB** вместе с рабочей памятью.
- Qwen3.6-35B-A3B-FP8 в том же сценарии: примерно **39–44 GiB**.
- Одна из них плюс embedding/reranker 0.6B: плановый суммарный диапазон **38–52 GiB**. Явно ограничить резерв памяти каждого процесса; не позволять каждому runtime резервировать почти всю GPU.
- **48 ГБ VRAM** — рабочий вариант с ограничениями: начинать с 1–3 последовательностей и коротких пакетов, тяжёлые модели при необходимости запускать по этапам. Для общей машины желательно минимум **64 ГБ системной RAM**. Ранее найденный тариф L40S с 32 ГБ RAM не равен этой комфортной конфигурации.
- **96 ГБ VRAM** — запас для текущего плана, но не доказательство достаточной пропускной способности.
- QLoRA 8B при microbatch 1, 2048 токенах и checkpointing: план **15–24 GiB VRAM**; на 48 ГБ отдельный эксперимент возможен. QLoRA не обязательна для выпуска.

Полное пользовательское время включает **очередь, холодный старт, поиск, загрузку/разбор, CPU, LLM, повторы, финализацию**. Условный расчёт второго прохода: 600 с остальных операций + 200 000/1000 входных токенов/с + 25 000/80 выходных токенов/с = **1112,5 с ≈18,54 мин**, без холодного старта. Остаток 87,5 с. Это бюджет при допущениях, не benchmark. Очередь входит в 20 минут; второй запрос без отдельного теста не получает такой гарантии.

Прежде чем брать GPU надолго, рекомендован короткий проверочный сеанс, первоначальный ориентир **2 часа**: загрузка pinned checkpoint, пик VRAM/RAM, скорость, полный анализ, сохранение и повторное чтение результатов. Большая загрузка весов может потребовать корректировки длительности. Проверить шесть областей и новое направление; отдельно очередь, холодный старт и фоновые загрузки. Ни одного такого аппаратного теста в этой задаче не выполняли.

## 6. Ручной опыт и его пределы

«Защита ИИ» и «Финтех»: в каждой области **8 табличных positives + 4 зрелых соседа + 2 гиперболических обещания + 1 шум = 15**. Прогоны A и B используют один пакет фактов и дают одинаковый результат:

- 4 верно оставлены; 7 контрольных верно исключены; 4 табличных остаются `U` — недостаточно/спорно подтверждены.
- Если U не выдавать: TP=4, FP=0, TN=7, FN=4. Правильных действий 11/15; точность короткого списка 4/4; сохранено только 4/8 positives.
- Это **не P@15 работающей системы**, не слепой тест и не результат поиска/LLM. В пуле всего 8 positives, поэтому он вообще не может доказать 12 попаданий.
- Защита ИИ: сохранены №2,4,49,76; U — №20,22,25,51.
- Финтех: сохранены №43,65,69,92; U — №15,39,71,93. По №93 сохранено разногласие: узкий банковский продукт можно принять, стадия всей категории не установлена.
- Причины U: недостающий контекст/функции, конфликт даты, нормативная допустимость вместо операции, продукт вместо состояния рынка. Менять только порог недостаточно; нужны факты или честно суженная категория и проверка смыслового match.

Шесть областей: Индустриальный ИИ, Инфраструктура ИИ, Роботы, Финтех — по 17; Защита ИИ и Edge — по 16. Отдельно рассмотрено длительное хранение тепловой энергии. Уже обсуждённое направление не считать новым слепым тестом без скрытых условий/пакета; окончательные новые запросы отложить до freeze.

## 13. Критерий приёмки другой, чем мы считали — разбор стенограммы 26.09 вечером

Файл `Документы от заказчика/Бизнес 1. Газпромбанк Тех.md` (66 КБ, сессия вопросов и
ответов, отвечает системный аналитик Газпромбанк.Тех) лежал у нас с начала и не был
разобран. В нём прямо сформулирован критерий приёмки.

**Оценивают не совпадение с таблицей.** «Позиционно несколько экспертов дают ответ, что
да, это слабый сигнал, нет, это не слабый сигнал. И исходя из вот этого количества да и
нет, высчитывается процент». Порог 75 %, «если будет больше 80, это лучше». Итоговое
тестирование — открытым запросом, в том числе по областям вне таблицы (назван пример
3D-печати). Сигнал вне таблицы засчитывается, если обоснован.

**Выдавать меньше пятнадцати разрешено.** «Если вы дадите 7 сигналов… мы будем оценивать
свои первые 7 и ваши первые 7. Возможно, вы попадёте в 100 %». Значит оптимизировать
надо точность, а не полноту: 15 позиций при 9 защитимых дают 60 % и провал.

**Методология заказчика — цикл хайпа Гартнера.** «Наш список на его базе основан».
Отбраковка: «большинство технологий… отметены либо по уже наличию большого количества
инвестиций, либо по уже большому количеству упоминаний и компаний». Верхней границы
зрелости у нас нет ни в каком виде — это главный пробел.

Прочее: ответ до 20 минут; запрос может быть узким («Микрофлюидный чип», «Гардрейл»),
а не только областью; иностранные источники разрешены, название по-русски, сопоставление
по смыслу; каждое название обязано иметь цитату или ссылку, иначе подозрение на
сгенерированное имя; заменяемость модели будут проверять; нужен интерфейс с полем
запроса и местом вывода; попросят живой запуск; отметённые кандидаты — плюс; ETL — плюс;
список доверенных источников предлагают составить самим.

Разбор отправлен GPT: `prompt-gpt6-astra-acceptance-criteria.md`.

## 14. Три проверенных метода, три отрицательных результата

**Путь гипотез** (`radar/hypotheses.py`, прогон 20260926-191011-гипотезы-финтех).
Модель предлагает категории, поиск подтверждает дословной цитатой. 16 гипотез, проверено
7 до дедлайна, подтверждено 5, судья дал **1 из 17** против 2 из 17 у пути обнаружения.
Вывод: генерация регрессирует к среднему независимо от источника. Планировщик скатывается
к структуре отрасли (open banking, CBDC), гипотезы — к штампам про ИИ в отрасли
(нейросетевой антифрод, генеративный дизайн продуктов). Эталон Финтеха — фронтир
(HTTP 402, Know Your Agent, Purpose-Bound Money) — не достигается ни тем, ни другим.

Побочно вскрылась слабость проверки: доказательствами приняты arXiv 2022 года по зрелой
теме, два личных репозитория на GitHub и два рекламных блога вендоров. Проверка отвечала
на вопрос «существует ли», а обязана отвечать на «раннее ли, растущее ли, не громкое ли».

**Метод отрицательного пространства** (эксперимент на 20260926-182222-финтех, 3 ₽).
Нулевая модель — 15 подсегментов планировщика, то есть зрелая структура области. Из 102
кандидатов уложилось 87, остаток 15 (15 %). Механика работает, но остаток оказался
наполовину посторонним материалом (HR, реклама, ритейл), а не фронтиром. Причина: я строил
одну ось «в структуре или нет», а нужны две — «в области» и «в структуре». Слабый сигнал
это пересечение «в области» и «вне структуры». Полезное наблюдение: внутриобластная
половина остатка кластеризуется вокруг идентичности и агентов, где и живут эталонные
№15, №69, №91. Остаток сохранён в `residual.json` прогона.

**Метод отрицательного пространства опровергнут** тем же вечером, два эксперимента, 9 ₽.

Замысел был: планировщик надёжно строит зрелую структуру области (это его доказанный
провал), значит берём остаток — то, что в структуру не укладывается, — и там живут слабые
сигналы. Проверка по двум осям на прогоне 20260926-182222-финтех: 89 зрелых, 13 вне
области, **0 в квадранте «в области, но вне структуры»**. Первая, одноосная версия давала
15 % остатка, но он целиком состоял из постороннего материала, и вторая ось его отсеяла.

Возражение «остаток пуст, потому что документы искались по самой нулевой модели»
проверено на независимом корпусе: 98 свежих сообщений Hacker News по запросам, не
содержащим названий сегментов. Результат: 52 вне области, 20 не технологии, 25 зрелых,
**1 в остатке** — любительский симулятор личных финансов.

Причина провала логическая. **Таксономия отрасли по построению исчерпывающа**: она и
создаётся так, чтобы всё в отрасли куда-то попадало. HTTP 402 укладывается в Real-Time
Payments, Know Your Agent — в AI Agents in Banking Operations, Purpose-Bound Money — в
CBDCs. То есть нулевая модель поглотила бы и эталонные фронтирные строки. «Не укладывается
в структуру» отбирает не новое внутри отрасли, а постороннее. Новизна и таксономическое
несоответствие — разные вещи.

Что выживает: две оси, которые задумывались вспомогательными, и есть главные — **возраст
термина** (чего не было в языке 18–24 месяца назад) и **громкость** (мало денег, компаний
и упоминаний, но растёт). Правильная рамка — окно зрелости с двумя границами, а не
отрицательное пространство. К идее остатка не возвращаться без нового довода.

**Эмбеддинги Codex (H1b)** — не подтверждены, детали в
`radar-codex/reports/claude-verification-2026-09-26.md`.

**Отдельно:** OpenAlex к вечеру заблокировал нас полностью (24 вызова, 24 отказа 429).
Нужен общий ограничитель частоты на процессы, иначе бесплатный источник отваливается
в самый нужный момент.

## 15. План на 27–28.09 в порядке приоритета

4. **Интерфейс** (Олег): поле запроса, вывод, список отметённых кандидатов.
5. **Отчёт, демо, живой запуск, отправка 28.09.**

## 18. Состояние кода на 27.09, 11:10

Новое с вечера 26.09, всё в `hackathon/radar/`:

- **`rank.py`** — окно зрелости с двумя границами. Верхняя из критериев заказчика:

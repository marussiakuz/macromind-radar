## 3. Ответы на вопросы 1–10

### 1. Метрика и число повторов

**[Оценка]** Определение C правильно: число различных категорий эталона с подтверждённым механизмом в пуле. Реализация сейчас измеряет лишь **число принятых предложений ограниченного матчером списка**. `suggest_matches` берёт максимум две эталонные строки на кандидата и порог 0,34; `judge` — максимум k кандидатов на эталон. Непоказанное соответствие никогда не будет принято. Добавляются ошибка жадного сопоставления и отсутствие обязательной проверки, что цитата доказывает механизм. Ноль может означать «не предложено», «не проверено», «ошибка ответа» или «нет» — эти статусы необходимо разделить.

**[Оценка]** Истинное покрытие **полностью проверенного объединения** — верхняя граница покрытия каждого входящего в него пула, если правило совпадения одно и наблюдения не теряются. Смешение конфигураций само по себе этой математике не мешает. Но нынешние 6/9 получены оценщиком с пропусками и ложными зачётами; при объединении дополнительно оставляется только первая запись каждого имени. Поэтому это **не доказанная верхняя граница даже для старых запусков**, тем более не для будущего гибрида. Допустимая подпись: «LLM предложила 9 соответствий в накопленном пуле четырёх разных конфигураций; независимое подтверждение не завершено». Слово «верхняя» убрать.

**[Рекомендация]** Хранить отдельно `C_pool`, `reference_match@15`, число выданных карточек, `factual_support`, `mature_in_top15`, `unknown_stage`. Основное требование — 12 **разных** совпадений в 15 финальных местах по каждой области. `C_pool ≥14` — разумный запас, но не доказательство достижения 12/15: фильтр и сортировка могут потерять все нужные позиции. По исходной смете три стоят **138–198 ₽**; после расширения считать заново. Не тратить этот бюджет на повторы заведомо дефектной версии. ### 2. Где узкое место

**[Оценка]** По трём добавленным парам top-15: №21 — ложный зачёт; №20 — не доказан сетевой/edge-уровень; №49 — содержательная новая находка, требующая проверки первоисточника. ### 4. Склейка

**[Рекомендация]** Сейчас **не снижать 0,75 и не переписывать всё на векторную БД**. Устранить потерю ссылок, затем разделить «наблюдение из документа» и «категория». Физически объединять исходные записи вообще не требуется: достаточно `cluster_id`, списка наблюдений и канонического имени. Перед ТОП-15 схлопывание эквивалентных категорий обязательно, иначе дубли займут места.

**[Рекомендация]** Ближайший вариант: `name_ru + name_orig + aliases`, нормализация словоформ для предложения пар; затем сравнение **механизма, объекта и контекста**. Ответ проверки — `эквивалент / родитель / частный вариант / различны / недостаточно данных`. Автосклейка только эквивалентов. Разные источники одной категории — не дубли доказательств; перепечатки одного события — не независимые подтверждения. Каноническое имя LLM не должно заменять исходный механизм и служить единственным ключом.

**[Оценка]** На несколько сотен наблюдений достаточно перебора предварительно отобранных пар в памяти. Исправление provenance и осторожная кластеризация — **2–3 ч**, входящие в план ниже; проверка ограниченного пакета пар моделью — ориентировочно **5–15 ₽**, зависит от токенов. Мультиязычные embeddings могут улучшить предложение пар, но это гипотеза: интеграция и проверка займут ещё **2–4 ч**, обучения не требуется. Даже хороший embedding не различает автоматически «родитель / эквивалент» и не исправляет неверные цитаты.

### 5. Менять ли способ обнаружения

**[Рекомендация] Мой выбор — гибрид, с ограничением объёма реализации.** Небольшая ветка generate-then-verify даёт 20–30 гипотез механизма/применения без эталона; существующая search-first даёт наблюдения из документов. После объединения обе ветки проходят одинаковую проверку. Включение гипотезы в поиск не означает включение в результат.

**[Оценка]** Знание отрасли в предобученной модели само по себе не делает C бессмысленным: это часть выбранного инструмента. Проблема — прямое включение ответов заказчика в инструкцию, многократная настройка на той же таблице и заявление об обнаружении новизны без датированных свидетельств. Search-first тоже использует знания LLM при планировании/извлечении и не гарантирует отсутствия такого влияния. Чистый generate-then-verify рискует выдавать известные родительские классы и искать лишь подтверждения; гибрид сохраняет шанс найти неизвестный модели механизм.

**[Рекомендация]** Для каждой гипотезы искать не только существование, но и опровергающие слабость факты: массовую стандартную поставку, давнюю доступность, отсутствие новой дельты, противоречащий источник. Разделить статусы `гипотеза / механизм подтверждён / стадия подтверждена / отклонено`. Генератору не показывать номера, названия и комментарии таблицы; verifier получает документы и проверяемые утверждения, а не желаемую метку «слабый».

**[Оценка]** Добавление ветки и маркировки происхождения — **2–3 ч** поверх исправленного конвейера; вместе с единой проверкой, отбором и карточками — **6–9 ч**, без фронтенда. Это выполнимый объём за два дня, но выигрыш в C **не измерен**. Продолжать только search-first — меньше работ сегодня, но оставляет зависимость от попавших в первые страницы материалов; полностью менять стек/модель — неоправданный риск срока.

**[Рекомендация]** Проверять гибрид так: фиксировать раздельный вклад веток до и после проверки; разрешать зачёт только по документу; все шесть областей считать известным открытым benchmark, «Защиту ИИ» — явно использованным dev. Остальные пять в этом прототипе ещё не запускались, но ранее обсуждались командой, поэтому не называть их полностью слепым holdout. Олег выбирает новое направление, не использованное в обзорах и промптах, до запуска; проверяет факты и экспертную пригодность по той же рубрике. Качество новых направлений не выражается совпадением с отсутствующей таблицей.

**[Оценка]** Пример бюджета полного гибрида: 4 seed + 20 discovery + до 48 verification = **до 72 Search-вызовов**; максимум 400 тыс. входных и 60 тыс. выходных токенов **на все стадии вместе**. По записанным тарифам `72×0,488 + 400000×0,0002 + 60000×0,0003 = 133,14 ₽`. Плановый лимит **150 ₽ на анализ** оставляет небольшой запас; это не замер и не гарантия, лимит должен реально прерывать дальнейшие вызовы. До 96 загрузок и ограниченный параллелизм — только при контроле общего deadline. Новую ветку добавлять внутри общего бюджета, не поверх безлимитного поиска.

### 10. Главный пропущенный риск и единственный дополнительный прогон

**[Оценка] Главный риск — система превращает настоящую цитату в неподтверждённую технологию или стадию.** После этого второй экземпляр той же LLM сопоставляет уже придуманное описание с эталоном, не видя доказательства. Найденный MCP-сканер из цитаты про атаку — прямой пример; `limited_sales` у исследовательского монитора — другой. Исправление лексического recall без проверки опоры может повысить отчётный C и одновременно ухудшить продукт.

**[Рекомендация]** Первым бесплатным измерением сделать аудит всех положительных пар судьи и пропущенного unlearning: для каждого существенного утверждения отметить `поддержано цитатой / опровергнуто / не установлено`. Этот аудит уже показал конкретные дефекты в §2.4, поэтому следующим шагом должен быть ремонт, а не ещё один запуск старой версии.

**[Рекомендация]** Если оплачивается ровно один новый полный прогон, после исправлений запустить **одну замороженную сквозную конфигурацию на «Защите ИИ»**. Главное измерение — **сколько из 16 механизмов действительно подтверждено в обработанных документах и сколько из них дошло до финальных 15 карточек**. Для каждого пропуска сохранить первую ступень потери и статус проверки; shortlist судьи не ограничивает человеческий аудит. Олег проверяет все финальные карточки, Марина — механизмы и спорные соответствия. Это одновременно проверит, вырос ли настоящий пул и не съедает ли его отбор. Не называть сравнение со старыми разными конфигурациями контролируемой абляцией.

**[Оценка]** Выбор именно этой области даёт проверяемые контрпримеры и связь с четырьмя прежними запусками; он **не проверяет перенос на остальные пять**. Если бюджет позволяет только прежние 46–66 ₽, а не плановые 150 ₽ полного пути, сократить discovery и число verification-пакетов, уложившись в денежный лимит; неполную проверку явно отметить. Не обещать одновременно полный аудит 15 карточек и прежнюю цену незавершённой половины конвейера.

### 13. Нужен ли Яндекс

**[Рекомендация]** Да: сайты небольших разработчиков, документация закрытых продуктов, релизы, внедрения у клиентов, интервью и сообщения инвесторов; поиск первичного источника по названию работы/компании; поиск противоречащих фактов и признаков зрелости. **[Рекомендация]** Использовать два режима: открытое обнаружение неизвестных доменов и точечная проверка с `site:`. Начальная доля открытого веба — не меньше трети веб-discovery, затем измерять добавочные доказанные механизмы; это проектная гипотеза, не оптимальный порог. Закрытый allowlist только крупных вендоров закрепит ту же ошибку, что `PRIMARY`: исключит новых участников рынка. Правило `site:` срабатывает на домен, а не гарантирует первичность каждой страницы.

**[Оценка]** 36% FARM в funding оправдывает изменение формулировок `startup raises seed series funding` и проверку пресс-релиза/инвестора, а не прекращение поиска. Подборка может быть хорошей точкой входа; источник суммы и факта закрытого раунда нужно найти отдельно. «Есть статья о привлечении» не равно «вся категория зрелая».

### 14. Как не вытеснить рынок тысячами препринтов

**[Рекомендация]** Балансировать **пакеты, дошедшие до извлечения**, не размер выдачи API. Начальная одинаковая политика для всех шести областей: из 48 пакетов — 24 на продукты/прототипы/кейсы, 12 на исследования, 6 на стандарты/официальные документы, 6 на сделки/внедрения. Это квоты типа материала, не домена: GitHub может дать research, а сайт компании — описание прототипа. Повторы версий и событий удаляются до занятия слота.

**[Рекомендация]** Внутри канала проходить подсегменты по кругу. Если слот пуст или документ не годится, фиксировать причину, затем отдавать его каналу с наибольшим числом ещё не покрытых подсегментов и готовым релевантным документом; научные материалы на первой версии ограничить половиной общего бюджета. Правило и все перераспределения сохраняются, номера эталона в нём не участвуют. Сортировать научный канал частично по свежести, частично по соответствию запросу: иначе несколько свежих версий кода вытеснят содержательную работу.

**[Оценка]** Эти квоты не доказаны оптимальными и могут потребовать изменения. Они обеспечивают проверяемый старт и предотвращают переполнение от одного API. На финальные 15 **не накладывать искусственную квоту «столько-то научных»**: после общей проверки ранней стадии и доказательств источник не должен определять место. Следить за `доказанные новые механизмы / пакет` и потерями каждого канала, а не за тысячами результатов в `meta.count`.

### 15. Качество академических источников

**[Рекомендация]** Не отсекать по минимальному числу цитирований и не запрещать Zenodo целиком. У нового исследования закономерно может быть ноль ссылок; Zenodo содержит также полезные данные и код. Вместо общего рейтинга применить последовательную проверку:

1. **Идентичность работы:** нормализованный DOI, arXiv ID без версии, отношения версий/публикации; совпадение заголовка и авторов предлагает пару на проверку. Concept DOI и version DOI — не два независимых события. Одного похожего заголовка для автоматической склейки недостаточно.
2. **Тип объекта:** paper/preprint отдельно от software, dataset, presentation и review. Код подтверждает существование артефакта, но не увеличивает счётчик научных статей. Препринт и статья по той же работе образуют семейство; новая версия может быть событием обновления, но не новой независимой работой.
3. **Техническая опора:** в abstract есть собственный метод, объект и конкретное утверждение, а не только обсуждение чужих исследований. Существенный для карточки факт, отсутствующий в аннотации, проверить по разрешённому полному тексту или оставить неизвестным. Авторское заявление не равно воспроизведённому результату.
4. **Независимость и статус:** хранить авторов, организации, review/acceptance, исправления/отзыв и качество доказательств. Несколько публикаций одной группы не считать независимыми внешними подтверждениями. Метка `article` в индексе не заменяет установленного peer review.

**[Оценка]** Самоцитирование влияет прежде всего на показатели влияния; при подсчёте уникальных работ оно не умножает число статей само по себе. Цитируемость — необязательный вспомогательный признак с учётом возраста и области, не критерий ранней стадии. Полный граф цитирований и расчёт самоцитирований за два дня имеют низкую отдачу.

### 16. Усиление сигнала по публикациям

**[Оценка]** `meta.count` — число записей, удовлетворяющих запросу; **это не рост**, не число уникальных исследовательских результатов и не вероятность слабого сигнала. `group_by=publication_year` даёт ряд таких количеств. Сумма после поиска с апреля 2025 не позволяет сравнить полные 2025/2026: оба окна урезаны по-разному. Неполный 2026 нельзя сравнивать с целым 2025 или линейно достраивать без модели сезонности/задержек.

**[Рекомендация] Минимальная честная версия:** зафиксировать словарь механизма и родительской области, типы документов, правила объединения семейства, версию индекса/дату получения. Считать два показателя раздельно: сырые количества индекса и доступные проверенные уникальные семьи. Если второй посчитан лишь на первых 10/30 ответах, он характеризует эту выборку, а не всю область. Формула `group_by` не выполняет вашу дополнительную дедупликацию Zenodo автоматически.

**[Рекомендация]** Для графика по годам — полные 2023–2025, а 2026 отдельно «по дату среза». Для сопоставления текущего года — одинаковые интервалы январь–август 2025 и 2026, с оговоркой о задержке индексирования. Для раннего ускорения лучше равные окна, например **12 недель против предыдущих 12**, заканчивающиеся за 28 дней до cutoff; lag 28 дней — начальная гипотеза, не известная задержка OpenAlex. Последние четыре недели продолжать использовать для discovery, но не смешивать с уже относительно устоявшимся рядом роста.

**[Рекомендация]** Пусть `n₀,n₁` — уникальные семьи конкретного механизма, `N₀,N₁` — семьи заранее заданной родительской области в тех же окнах и источниках. Тогда показывать абсолютный прирост `Δ=n₁−n₀` и относительное изменение доли:

```text
s₀ = (n₀ + 0,5) / (N₀ + 1)
s₁ = (n₁ + 0,5) / (N₁ + 1)
G = s₁ / s₀
```

**[Оценка]** Сглаживание не делает слабые данные убедительными: рост с нуля до одной работы следует обозначить как «первое наблюдение», а не сильное ускорение. Если тема выросла 10→20, а вся область 100→200, сырой рост двукратный, но доля примерно неизменна. Если 2→8 при области 100→110, сглаженный `G ≈3,09`; это повод проверить новое исследовательское внимание, не автоматически оставить категорию в ТОП-15.

**[Гипотеза]** Для экспериментального флага, а не фильтра зрелости, можно начать с `n₁≥5`, `Δ≥3`, `G≥1,5` и нескольких независимых исследовательских групп. Все пороги требуют проверки; четыре поисковые пробы их не обосновывают. При малом числе работ публиковать сами количества и неопределённость, не дробный балл уверенности. При проверке десятков тем учитывать, что случайные всплески будут встречаться чаще.

**[Рекомендация]** Формы запросов для **сырых**, ещё не дедуплицированных индикаторов:

```text
GET https://api.openalex.org/works
filter=title_and_abstract.search:machine unlearning,from_publication_date:2023-01-01,to_publication_date:2025-12-31
group_by=publication_year

# Один сопоставимый период текущего года; предыдущий — с теми же месяцами 2025:
filter=title_and_abstract.search:machine unlearning,from_publication_date:2026-01-01,to_publication_date:2026-08-31
group_by=type
```

**[Факт]** Семантика `group_by` и счётчиков документирована [OpenAlex](https://help.openalex.org/api/grouping/). **[Не проверено]** Эти новые группировочные запросы в этой рецензии не запускались; научная релевантность полученных групп и полнота индекса не измерены.

**[Рекомендация]** До сдачи рост — вспомогательное объяснение для исследовательских категорий, максимум дополнительный критерий при равных доказательствах. Отсутствующий ряд — `unknown`, не штраф коммерческой категории. Фраза «без публикационного роста нечем ранжировать» неверна: уже доступны подтверждённая новая дельта, стадия реализации, независимые применения и зрелый сосед. Рост науки не может заменить проверку зрелости рынка.

### 17. Файлы, SQLite, сервер и совместная разметка

**[Факт]** Четыре живых каталога занимают по сумме размеров файлов **83 607 043 байта = 83,61 МБ = 79,73 МиБ**. Сырой HTML по прогонам: **25,34; 21,09; 14,83; 14,41 МБ**. «81 МБ» передаёт порядок объёма, но диапазон «14–20 МБ сырья» не включает два первых запуска. Это не объём, который сам по себе требует отдельной серверной СУБД.

**[Оценка]** При сохранении среднего размера около 21 МБ и десяти прогонах в день получится около 210 МБ/день, или 3 ГБ за две недели без резервных копий. Это экстраполяция четырёх запусков одной области; PDF, другие области и более глубокое извлечение могут изменить её. Основная причина базы сейчас — состояния задач, общая разметка и история, а не нехватка диска.

**[Факт]** SQLite — полноценная транзакционная БД. В режиме WAL чтение и запись могут идти одновременно, но одновременно выполняется только одна пишущая транзакция. Процессы, работающие с WAL, должны находиться на одном хосте; сетевой файл базы между компьютерами разметчиков не подходит. Два человека, обращающиеся браузерами к одному API, этому ограничению не противоречат. [Документация SQLite](https://www.sqlite.org/wal.html)

**[Рекомендация] Выбор для команды:** сохранить неизменяемые JSONL/raw как артефакты прогонов, а для стенда и состояния приложения использовать **небольшую PostgreSQL в уже выбранном стеке**. Не переносить туда весь архив HTML и не внедрять сейчас pgvector ради самого факта наличия RAG. Отдельный промежуточный слой SQLite с последующей миграцией создаёт вторую работу. Если серверный контур совсем не готов и SQLite позволяет запустить внутренний стенд сегодня, она допустима как явно временный вариант на одном хосте; одновременная работа двух разметчиков сама по себе не требует перехода на PostgreSQL.

**[Рекомендация]** Минимальные сущности: прогон, версия кандидата, ссылка на документ/цитату и решение проверяющего. Для решения хранить `reviewer_id`, время, версию рубрики, версию кандидата, вердикт и комментарий. Независимые оценки Марины и Олега сохранять раздельно; согласование — отдельная запись, не перезапись чужой оценки. При редактировании применять проверку версии записи, чтобы позднее сохранение не затёрло новое. Транзакции короткие: сетевой вызов LLM не держит блокировку БД. JSONL становится экспортом, а не общим файлом, который одновременно переписывают два браузера.

**[Оценка]** Минимальная схема, запись решений и идемпотентный импорт метаданных — **2–3 часа Марины**, без полноценного интерфейса и переносов всех артефактов. Развёртывание доступного извне API/UI — ещё **1–2 часа** при готовых контейнерах; интерфейс уже учтён в плане Олега. Если эти предпосылки отсутствуют, оценка увеличивается. Резервную копию БД и файлов проверять восстановлением; для SQLite не копировать только основной файл активной WAL-базы.

**[Оценка]** Для двух разметчиков, одного фонового анализа и удалённых моделей разумная стартовая VM — **4 vCPU, 8–16 ГБ RAM, 100 ГБ SSD**, без GPU. Это оценка для нынешнего небольшого прототипа с API, не новый benchmark полноценного локального RAG и не замена прежней конфигурации под локальную Qwen. Наличие сервера не установлено, аренда не выполнена; актуальная цена этой корзины здесь не проверялась. Использовать уже доступный хост, если он есть, либо отдельно проверить цену минимальной VM. Большая GPU и управляемый кластер БД покрытие не улучшат.

**[Рекомендация]** Уточнение прежнего «не делать новую БД»: не откладывать совместную разметку и сохранность решений; откладывать полный перенос конвейера, векторный индекс и сложную инфраструктуру. Хост нужен для доступного стенда и демонстрации, а сам CLI-прогон может продолжать работать с файлами.

### 18. Лимиты и вежливость к бесплатным API

**[Факт]** По актуальной документации OpenAlex анонимная дневная квота — **$0,10**, с бесплатным аккаунтом/ключом — **$1**. Поисковый вызов стоит **$0,001** из этой квоты; другие классы запросов тарифицируются иначе. Наш `title_and_abstract.search` внутри `filter` тоже расходовал по $0,001: это подтверждено заголовками четырёх ответов. Поэтому «ключ не нужен» верно для пробы, но недостаточно для запланированного объёма. [Тарифные примеры](https://help.openalex.org/access/example-costs/)

**[Оценка]** `36 × 10 = 360` поисковых вызовов стоят **$0,36 дневной квоты** до пагинации и повторов. Анонимной квоты не хватает, бесплатного ключа — хватает при отсутствии значительной другой нагрузки аккаунта. Четыре выполненные здесь пробы использовали $0,004 бесплатной квоты; **денежных платежей не было**. Если один логический запрос разбит на страницы или дополнительные интервалы для графика, каждый HTTP-вызов учитывать отдельно.

**[Факт]** OpenAlex документирует верхний предел 100 запросов/с, ограничения дневного бюджета, HTTP 429 и заголовки остатка. Это предел провайдера, не рекомендуемый темп для нашего стенда. [Аутентификация и лимиты](https://help.openalex.org/api/authentication/)

**[Рекомендация] OpenAlex:** один общий ограничитель на весь worker/аккаунт, начать с **1 запроса/с** и одного соединения; собственный дневной потолок — 80 поисковых вызовов без ключа либо 800 с бесплатным ключом, дополнительно контролировать реальный остаток из заголовков. Эти потолки оставляют около 20% запаса только при таком же классе запросов и отсутствии другой нагрузки. При 429 учитывать `Retry-After`, если он есть; ограниченный backoff с небольшим случайным сдвигом, затем статус `rate_limited`, а не бесконечные повторы. Ключи удалять из логов URL и manifest.

**[Факт]** Для legacy arXiv API официальные условия требуют не чаще одного запроса каждые три секунды и одного соединения; ограничение следует соблюдать суммарно, а не отдельно в каждом экземпляре адаптера. [Условия arXiv API](https://info.arxiv.org/help/api/tou.html)

**[Рекомендация] arXiv:** после восстановления доступности — одна очередь на все процессы, **интервал 5 секунд** как наш консервативный запас, понятный User-Agent с настоящим контактом. 360 запросов при таком интервале занимают около 30 минут суммарно за день; это арифметика расписания, не гарантия допуска. Сейчас повторные 406 прекращать после первой ограниченной проверки и отключать провайдера на прогон. Причина 406 не установлена; пауза не гарантирует разблокировку. Не менять адреса/прокси ради обхода отказа. Пока доступ не подтверждён, производственный путь использует OpenAlex и веб.

**[Рекомендация] Для обоих источников:** кешировать успешный ответ по полному нормализованному набору параметров, источнику и версии схемы; читать кеш перед вызовом. Для обычного discovery начать с TTL 24 часа, для замороженной оценки хранить неизменяемый снимок. Ошибка доступа, timeout, пустая выдача и успешный ответ — разные состояния. Отказы не превращать в долговременный кеш «работ нет». Сохранять время получения, HTTP-статус, число попыток, задержку, идентификаторы работ и расход квоты; ограничивать повторы общим остатком 1200 секунд на прогон.

**[Рекомендация]** Не умножать все 36 веб-запросов на число новых источников. Маршрутизировать только исследовательскую часть, переиспользовать ответы одинаковых подсегментов между запусками и начинать с одной страницы 10–20 результатов. Полный подсчёт временных рядов вынести из синхронного ответа аналитику. Бесплатный научный поиск не делает бесплатным последующее LLM-извлечение: его пакеты остаются в общем лимите.

### 7.3. Как дополнение меняет двухдневный план

**[Рекомендация]** Порядок остаётся прежним: исправление потерь документов и доказательств → законченная карточка → проверка всех шести областей. OpenAlex встраивается между первым и вторым шагом с жёстким пределом **3 часа**. Новая ветка должна выдать сохранённый abstract с ID, датой, типом и цитатой через общий контракт, а не только большое `meta.count`. Если интеграция не укладывается, оставить целевой научный веб-поиск и закончить карточки.

| Изменение относительно §5 | Марина | Олег | Расходы и условие |
|---|---:|---:|---|
| OpenAlex: один адаптер, маршрутизация, слоты, кеш и явные ошибки; проверка одного научного пакета | +3 ч максимум | Внутри проверки карточек | API в бесплатной квоте; LLM-пакеты заменяют часть прежних 48, а не добавляются сверх них |
| Сохранение независимых оценок и конфликтов редактирования в минимальной БД | +2 ч к уже заложенным интеграции UI/развёртыванию | +1 ч на элементы разметки | Хост отдельно; без переноса всего архива и без векторного индекса |

**[Рекомендация]** Команда выше берёт все живые прогоны, в том числе добавленные после этой проверки; поэтому её новые общие доли могут отличаться. Для воспроизведения именно рассмотренной выборки нужен явный список четырёх каталогов. Пересчёт состава, слоёв и логического объёма файлов без сети:

```python
import json
from collections import Counter
from pathlib import Path
from urllib.parse import urlsplit
from radar.hoststats import layer_of

hosts = Counter()
layers, candidate_layers = Counter(), Counter()
total_bytes = candidates = 0
run_names = [f'20260926-{stamp}-защита' for stamp in ('091119', '092118', '092705', '110340')]
for run in [Path('radar-runs') / name for name in run_names]:
    manifest = run / 'manifest.json'
    if not manifest.exists():
        continue
    if json.loads(manifest.read_text())['mode'] != 'live':
        continue
    hits = [json.loads(s) for s in (run / 'hits.jsonl').read_text().splitlines() if s.strip()]
    rows = [json.loads(s) for s in (run / 'candidates.jsonl').read_text().splitlines() if s.strip()]
    for hit in hits:
        host = (urlsplit(hit['url']).hostname or '').lower().removeprefix('www.')
        hosts[host] += 1
        layers[layer_of(host)] += 1
    for row in rows:
        host = (urlsplit(row['source_url']).hostname or '').lower().removeprefix('www.')
        candidate_layers[layer_of(host)] += 1
    size = sum(p.stat().st_size for p in run.rglob('*') if p.is_file())
    raw = sum(p.stat().st_size for p in (run / 'raw').rglob('*') if p.is_file())
    print(run.name, len(hits), len(rows), size, raw)
    total_bytes += size
    candidates += len(rows)
print('hits, hosts, candidates, bytes:', sum(hosts.values()), len(hosts), candidates, total_bytes)
print('hosts seen 1–2 times; their positions:',
      sum(n <= 2 for n in hosts.values()), sum(n for n in hosts.values() if n <= 2))
print('layers:', dict(layers), 'candidate layers:', dict(candidate_layers))
# На четырёх рассмотренных live-прогонах: 900, 481, 475, 83607043; затем 402, 488.
```

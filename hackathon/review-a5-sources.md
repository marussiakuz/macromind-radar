## A5. Источники данных

На хакатоне обучаем небольшой ранжировщик на исторических рядах публикаций. Qwen используем без дообучения: извлечение терминов из предоставленных документов, проверка типа кандидата и карточки с доказательствами. Будущее дообучение LLM — отдельный набор инструкций и проверенных ответов, отдельная проверка прав и отдельный бюджет.

Проверка веб-страниц выполнена через поисковый сервис; запросы с IP выбранного российского сервера не выполнялись. Поэтому ни для одного зарубежного API не заявляем фактически подтверждённую доступность из России.

### Что исправить в доступе OpenAlex

Фраза Claude «с 13.02.2026 ключ обязателен» не соответствует действующей августовской справке: сейчас разрешён небольшой бюджет без ключа. Ключ всё равно создаём сразу, секрет храним только на сервере. Для полной выгрузки берём курсоры, `select`, возобновление по checkpoint и кэш ответов. [Действующая аутентификация](https://help.openalex.org/api/authentication/) — 13.09.2026.

При 100 записях/страницу ≈60–100 тыс. записей потребуют минимум ≈600–1 000 страниц. Для list/filter это ≈$0,06–0,10 = число запросов × $0,0001; для search ≈$0,60–1 = число запросов × $0,001. Это нижняя оценка без пересечений, пустых страниц, повторов и проверки полноты. По `count` оцениваем объём до запуска; не обрезаем исторический корпус произвольным лимитом и не выдаём усечённые результаты за полные годовые количества. [Тариф операций](https://help.openalex.org/access/example-costs/) — 13.09.2026.

Публичный snapshot сейчас обновляется ежеквартально и доступен анонимно на S3; ежедневный snapshot — платная возможность. Он содержит сегодняшнее представление исторических записей, а не гарантированный архив «что сервис знал в 2019 году». Для двух направлений API проще полной выгрузки. [Продукты](https://help.openalex.org/access/overview/), [snapshot](https://help.openalex.org/access/snapshot/) — 13.09.2026.

### Исторические данные и эталоны

Олег формирует два разных набора. Первый — контроль покрытия кандидатов: план ≈60–100 тем = 2 направления × 30–50 тем, выбранных из датированных обзоров и корпуса на дату T, до просмотра результата T+5. Второй — случайная стратифицированная проверка тем из полного пула кандидатов: страты по направлению, году, видимости и признаку роста; исходы скрыты при проверке «это технология» и релевантности. Целевой recall кандидатов ≥80 % проверяем на первом наборе. Precision@15 и recall@15 считаем на полном тестовом пуле с формально рассчитанными исходами, не на искусственном списке из равного числа успехов и неудач.

Материалы для исходного списка: датированные научные обзоры и proceedings, списки тем исследовательских программ, старые технологические дорожные карты и отчёты авторов программ. Конкретные документы берём из собранного корпуса; сохраняем дату публикации, страницу и цитату для каждого названия. Современные «топ технологий» и память LLM подходят только для иллюстраций после замораживания теста. Они заранее отбирают известные успехи и меняют сложность задачи.

«Выросла» означает достигла заранее зафиксированного публикационного исхода, а не доказала рыночный успех. Пороги N и X выбираем на разработочной части train/dev и фиксируем до final test по A3. Отрицательная метка означает «исход не достигнут за полные 5 лет наблюдения»; не называем её «технология заглохла». Тема с неполным окном, пропуском корпуса или неясной склейкой синонимов получает `censored`/`unknown` и исключается из бинарной оценки. Отсутствие в очередном отчёте не создаёт нулевую метку. Отрицательные примеры выбираем из того же исторического пула по этим правилам, затем вручную разбираем переименования и объединения технологий.

Публикационные количества считаем по полному для выбранных границ запросу. Если корпус получен только поиском нескольких сегодняшних подтем, знаменатель «доля направления» неверен: нужна одинаковая стабильная процедура отбора направления для всех лет. Препринт и журнальную версию объединяем в одно исследование; публикация не может удваивать рост. «Первое упоминание» подписываем как первое найденное упоминание в покрытом корпусе; если история начинается с 2010 года, найденная в 2010 году тема имеет неизвестный истинный возраст, а не нулевой.

Для честного ретро-эксперимента недостаточно фильтра `publication_year <= T`. Текущие аннотации, тематические классификации, исправленные организации, число цитирований и доступность записей могли измениться после T. Исторические термины извлекаем из документированной версии текста, опубликованной не позже T. LLM не расширяет ретро-кандидатов свободными знаниями; допустима только обработка предоставленного исторического текста с проверяемыми упоминаниями. Синонимы фиксируются отдельно в каждом срезе; сегодняшняя склейка не переносится в прошлое. Признаки цитирования исключаем до наличия рёбер с датами цитирующих документов и понятной полнотой.

Даже пересчёт по датам не устраняет последующее включение старой публикации в базу. При отсутствии исторических архивов результат называем «ретроспективная реконструкция по корпусу, полученному 13.09.2026», а не строгий backtest без утечки. Строгую гарантию можно дать лишь для среза с доказуемой доступностью каждого входа на дату T. С 13.09 сохраняем неизменяемые ответы, `retrieved_at`, версию источника, контрольную сумму и manifest выборки для будущей проспективной проверки.

### Русскоязычные источники за две недели

Делаем русский интерфейс, русские названия и мотивацию с доказательствами из международного корпуса. Добавляем российские исследования, уже присутствующие в OpenAlex, и проверенные вручную патентные кейсы. Полноценные коннекторы eLibrary и КиберЛенинки не помещаются в обязательный объём; у КиберЛенинки есть прямое ограничение автоматизации. Роспатент берём точечно, если нужные документы действительно усиливают карточку; отсутствие патента не снижает научный рейтинг. Патентные семьи дедуплицируем, дату доступности считаем от публикации документа, а не закрытой даты приоритета.

### Данные для будущего дообучения LLM

Начинаем с малого пилота SFT после анализа ошибок текущего RAG. План ≈2 000–5 000 примеров = 5 задач × 400–1 000 проверенных примеров: извлечение технологии, синонимы, привязка утверждения к фрагменту, русская карточка в JSON и корректный отказ при недостатке доказательств. При среднем ≈2 000 токенов на пример это ≈4–10 млн токенов за эпоху. Это проектная оценка, достаточность проверяется кривой качества на закрытом тесте.

Выделяем по документам и семействам технологий отдельные train/validation/test, например 80/10/10 %; производные одного документа не расходятся между частями. До генерации синтетики фиксируем тест. Часть разметки должна включать противоречивые источники, нерелевантные фрагменты и отсутствующие доказательства. Проверяем не стиль ответа, а долю подтверждённых утверждений, корректность JSON, полноту извлечения и число необоснованных заявлений. Синтетические ответы без ручной проверки доказательств не становятся эталоном.

Для дальнейшего preference tuning план ≈1 000–3 000 пар = 5 типовых ошибок × 200–600 сравнений с объяснением выбора. Продолженное предобучение на научном корпусе в пилот не включаем: сначала проверяем, исправляет ли SFT измеримые ошибки. Источник текста и права фиксируются для каждого примера; для полнотекстового обучения используем собственную разметку и документы с подходящими разрешениями, не переносим CC0 метаданных на PDF. Банковские документы при появлении остаются в локальном контуре и не отправляются провайдерам моделей.
